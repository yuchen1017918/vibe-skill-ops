# 快照笔记（Snapshot Notes）— 跨对话工作记忆

**问题**：对话上下文会丢（新会话/超长对话/切换平台），重新开始就要重复解释项目状态。
**方案**：在**项目根目录**建 `.snapshots/` 文件夹，Agent 定期写入项目快照；
新会话先读快照，秒级恢复上下文。

> 与 `agent-project-manager` 分工：它是**集中式**多项目管理（`workspace/projects/`）；
> 本 skill 是**项目内嵌式**轻量快照（`.snapshots/` 跟随项目、随 git 走）。两者可并存。

## 📁 目录结构（v1.1 版本链）

```
<项目根>/
├── .snapshots/              # ← 快照文件夹（项目根目录下）
│   ├── SNAPSHOT.md          # 当前有效快照（始终指向最新，覆盖更新）
│   ├── SNAPSHOT_INDEX.json  # 快照版本索引（v1.1 新增）
│   └── history/             # 历史版本（保留完整演进轨迹）
│       ├── 2026-08-06-0930.md
│       └── 2026-08-06-1500.md
├── .gitignore               # 如需不入库可加 .snapshots/（默认建议入库）
└── ...项目文件
```

### SNAPSHOT_INDEX.json 格式（版本链核心）

```json
{
  "project": "项目名",
  "current": "2026-08-06-1500",
  "versions": [
    {"id": "2026-08-06-1500", "file": "history/2026-08-06-1500.md", "stage": "Phase 2", "created": "2026-08-06T15:00:00+08:00", "author": "main"},
    {"id": "2026-08-06-0930", "file": "history/2026-08-06-0930.md", "stage": "Phase 1", "created": "2026-08-06T09:30:00+08:00", "author": "spec-writer"}
  ],
  "conflicts": []
}
```

- `current`：当前有效版本 ID（始终等于最新 SNAPSHOT.md 内容对应版本）
- `versions`：版本链（新版本前插，最多保留 30 条，超出归档到 history/archive/）
- `conflicts`：冲突记录（由 agent-collab 状态对齐流程写入）

## 🔔 写入时机（Agent 必须自动执行）

| 时机 | 动作 |
|------|------|
| **每个阶段/里程碑完成** | 更新 SNAPSHOT.md |
| **重要决策**（技术选型/架构变更/方案取舍） | 记入"关键决策"段 |
| **踩坑并解决** | 记入"坑与解法"段（下次不重踩） |
| **对话结束前**（用户说"记住/保存/先到这"） | 写快照 + 归档历史 |
| **上下文快满**（感觉要丢信息） | 立即写快照再继续 |
| **新会话开始** | 先读 `.snapshots/SNAPSHOT.md` 恢复 |

## 📝 SNAPSHOT.md 模板

```markdown
# 项目快照 — [项目名]

## 概要
- 一句话：<项目做什么>
- 技术栈：<前端+后端+数据库+工具>
- 当前阶段：<Phase X / 调研 / 重构 …>
- 最后更新：<时间戳>

## 已完成 ✅
- [x] <里程碑/功能/决策>

## 进行中 🔄
- [ ] <当前任务>（下一步做什么，卡在哪）

## 待办/下一步 ⏭
1. <优先级最高的下一步>

## 关键决策 🧠
| 决策 | 选择 | 理由 | 替代方案 |
|------|------|------|----------|
| <技术选型等> | <选了啥> | <为什么> | <没选啥> |

## 坑与解法 ⚠️
| 坑 | 症状 | 解法 |
|----|------|------|
| <踩过的坑> | <现象> | <怎么解决> |

## 关键文件 📄
- <路径>：<作用>（入口/核心逻辑/配置）

## 待验证 ⏳
- <还没确认的假设/测试>

## 交接提示 🤝
- <下一个接手 Agent/会话最需要知道的一件事>
```

## 🩺 健康度检查 v2.0（v1.3 升级 — 冲突报告 + 人工确认）

**目的**：长期运行后，快照可能偏离真实项目状态（git 历史/文件结构变化）。
**v2.0 核心变更**：⚠️ **禁止自动写操作**——"自动对齐"可能反向恢复已删除代码或覆盖新代码（数据丢失风险）。
所有对齐动作必须显式确认。

### 触发时机
- **新会话加载快照时**（恢复上下文前）
- **写入快照前**（更新前先验证基线）

### 检查项（轻量，秒级）

| 检查 | 命令 | 不一致处理 |
|------|------|------------|
| Git HEAD 校验 | `git rev-parse HEAD` vs 快照记录的 commit | 不一致 → 冲突分类 |
| 未提交改动 | `git status --porcelain` | 有改动 → 冲突分类 |
| 关键文件指纹 | `sha256sum package.json go.mod pyproject.toml`（有则算） | 变更 → 优先复查依赖/配置 |

### 冲突分类（v2.0 核心 — 比对后分类，不直接动手）

| 状态 | 判定 | 动作 |
|------|------|------|
| 🟢 一致 | 快照 ≈ git 状态 | 无操作，继续恢复 |
| 🟡 快照超前 | 快照有新代码，git 没有 | **提示**"是否应用快照变更？"（默认否，确认后应用） |
| 🟠 git 超前 | git 有新提交，快照没有 | **提示**"是否更新快照基线？"（默认是，确认后更新） |
| 🔴 双向漂移 | 同一处代码快照和 git 都改了 | **强制人工介入**：输出 git diff 对比，等用户裁决，禁止自动选择 |

### 对齐流程（显式确认制）

```
1. 比对 → 分类（🟢🟡🟠🔴）
2. 按分类动作执行（🟡🟠 需确认；🔴 强制人工）
3. 更新 SNAPSHOT.md 后追加对齐记录：
   "[YYYY-MM-DD HH:MM] 状态对齐：🟠 git 超前 X commits，已确认更新快照基线"
4. 用对齐后的快照继续恢复流程
```

> 安全例外：仅当配置 `--auto-align-safe` 时，🟡（快照超前）可自动应用，其他状态仍需确认。
> 原则：**快照是参考不是权威**，真实 git 状态才是事实源。

### 🧠 用户确认偏好（v1.5 新增 — 从统一 SLA 到个性化交互）

**目的**：不同用户对确认容忍度不同——有人全要阻塞，有人全要通知。

- **偏好学习**：用户连续 3 次对同一类确认选择"默认策略/跳过" → 自动记录偏好，
  该类确认降级为自动执行（记录在 `.vibe/user-prefs.yml`）
- **临时覆盖**：`/confirm-strict`（全部阻塞）/ `/confirm-lax`（全部通知），
  覆盖后记住偏好，防"误学习"
- **重置**：`/confirm-reset` 清空偏好，回到统一 SLA

### 📊 复杂度校准记录（v1.3 新增 — Triage 动态反馈）

**目的**：让 L0/L1/L2 判定从"静态规则"变"动态学习"——记录实际执行 vs 初始判定偏差。

每次任务完成后（plan-workflow / agent-loop 触发），在 SNAPSHOT.md 记录：

```markdown
## 复杂度校准（最近 10 条）
| 任务 | 初始判定 | 实际耗时 | Token 消耗 | 返工次数 | 偏差 |
|------|----------|----------|------------|----------|------|
| 改 i18n 文案 | L0 | 45min | 12k | 3 | ⚠️ 低估 |
```

**动态校准规则**：
- 同一类任务多次"低估"（如 CSS 改动返工率高）→ 自动将该类任务从 L0 提升到 L1（强制完成前验证）。
- 多次"高估"→ 降级，减少不必要流程。
> 校准数据沉淀到 `~/.vibe/metrics/triage-accuracy.log`，月度复盘。

### 🗺 项目上下文画像（v1.4 新增 — Triage 上下文感知）

**目的**：同一任务在不同项目复杂度不同（"改单文件"在单体项目是 L0，在微服务可能是 L1）。
Triage 判定时读取项目画像做动态加权。

**生成时机**：`project-scaffold` 初始化时 / 首次 `plan-workflow` 时自动生成 `.vibe/project-context.yaml`：

```yaml
project:
  name: <项目名>
  architecture: monolith | microservices | modular   # 架构复杂度
  module_count: <模块数>
  tech_stack: [<技术栈>]
  coupling: high | medium | low        # 模块耦合度（可基于 import 分析）
  sensitive: [auth, payment, user-data] # 敏感域
```

**Triage 动态加权**（v3.5 起生效）：
- 微服务/高耦合项目 → "是否被 import"、"是否 3+ 模块联动"权重自动提升（更易判为 L1/L2）
- 含敏感域 → 问题 5 直接命中 → L2 + 强制 security-audit
- 单体低耦合项目 → 判定权重下降（更多任务可走 L0/L1，省 token）

> 无画像时回退到通用判定清单（保持现状）。画像数据也可供 knowledge-extraction 复盘引用。

### 🌐 跨设备快照同步（v1.4 可选模块 — 不强制）

**目的**：单设备快照在"公司电脑/家里电脑/云端"之间隔离。以下方案可选启用。

**方案 A：Git 仓库作为载体（零额外基础设施，推荐）**
- 项目级快照自动存入项目仓库的 `.vibe/snapshots/` 分支
- 跨设备 `git pull` 即可恢复
- 沿用现有 git 权限体系，无需新配置

**方案 B：加密云同步（跨项目统一恢复点）**
- 配置 `~/.vibe/sync.yml`：
  ```yaml
  provider: s3/r2/onedrive
  encrypt: true   # 快照可能含敏感代码片段
  auto_sync: push_on_snapshot, pull_on_restore
  ```

**冲突处理**：设备 A/B 各自创建快照 → 按时间戳合并 → 双向漂移走健康度检查 v2.0 的 🔴 冲突四分类（强制人工）。

> 默认不启用（零配置原则）；用户明确配置后才同步。

## 🔄 恢复流程（新会话）

1. 检查项目根目录是否存在 `.snapshots/SNAPSHOT.md`。
2. 存在 → 读取，用快照内容恢复上下文（不用用户重新解释）。
3. 不存在 → 初始化：创建 `.snapshots/`，写入首个快照。
4. 恢复后向用户确认："已从快照恢复，上次进行到 <X>，下一步是 <Y>，继续？"

## 💾 写入流程（v1.1 版本链）

```
1. 确认项目根目录（存在 .git 或项目标志文件）
2. 生成版本 ID：TS=$(date +%Y-%m-%d-%H%M)
3. 旧快照归档：cp .snapshots/SNAPSHOT.md .snapshots/history/${TS}.md
4. 按模板写新 SNAPSHOT.md（保持简洁，不堆砌）
5. 更新 SNAPSHOT_INDEX.json：
   - versions 前插 {id: TS, file: history/TS.md, stage, created, author}
   - current = TS
   - 超出 30 条 → 最旧的移到 history/archive/
6. 若有 git：git add .snapshots/ && git commit -m "docs: 快照 v$TS"
```

### 🔄 冲突检测（版本比对）

**何时比对**：子Agent 汇报前 / 多Agent并行阶段 / 新会话恢复前。

```
比对方法：
1. 读 SNAPSHOT_INDEX.json 的 current
2. 读当前 SNAPSHOT.md，解析"当前阶段 + 进行中"字段
3. 与自己任务上下文比对：
   - 阶段一致 → 无冲突，继续
   - 阶段不一致（自己以为在 Phase 2，快照显示 Phase 3）→ 触发状态对齐
```

**状态对齐流程**（发现冲突时）：
```
1. 停止当前任务（不盲目执行）
2. 读最新 SNAPSHOT.md 全文，重建最新上下文
3. 向主Agent 报告冲突：期望状态 vs 实际状态
4. 主Agent 裁决：更新任务 / 重派 / 修正快照
5. 在 SNAPSHOT_INDEX.json 的 conflicts 数组记录该事件
6. 对齐完成后继续任务
```

**冲突等级**：
| 等级 | 判定 | 动作 |
|------|------|------|
| 🟢 轻微 | 阶段相同，任务细节微差 | 采纳快照，继续 |
| 🟡 中等 | 阶段不同，但任务仍有效 | 状态对齐后继续 |
| 🔴 严重 | 阶段/任务完全矛盾 | 停止，上报主Agent裁决 |

## ✍️ 编写原则

- **简洁**：快照是索引不是文档，5 分钟能重读恢复为准（目标 <100 行）。
- **高频更新**：宁可多写几次短的，不要攒到最后写一大篇。
- **决策必记**：任何"为什么选 A 不选 B"都值得记，跨对话最容易丢的就是理由。
- **坑必记**：踩过的坑写下来，下次直接避开。
- **不重复**：与 `agent-project-manager` 的 STATUS.md 信息重叠时，快照保持精简指针（"详见 STATUS.md"）。

## 与全家桶其他 skill 的配合

- `vibe-coding` / `dev-team`：每个 Phase 完成时触发写快照。
- `agent-project-manager`：集中式项目管理；快照笔记做项目内轻量补充。
- `git-workflow`：快照随 git 提交，历史可回溯。
- `code-wiki`：快照管"进行时"，wiki 管"沉淀后"。

## 快速排障

| 症状 | 处理 |
|------|------|
| 找不到项目根目录 | 找 .git 或 package.json/pyproject.toml 标志文件 |
| 快照太长 | 压缩：只留决策/坑/下一步，细节指向文档 |
| 多项目混乱 | 快照一定放各自项目根目录，不共用 |
| 忘了写快照 | 每次工具调用后自检：这个结果重要吗？重要就记 |
