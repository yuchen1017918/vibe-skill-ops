# 提交前安全审计（Security Audit）

**目的**：Vibe Coding 生成代码速度快，但极易带安全漏洞（未加密状态、弱权限验证、硬编码密钥）。
本 skill 在"代码生成后、提交前"做一次轻量安全扫描，守住上线底线。

## 🚨 触发时机（提交前强制）| 时机 | 说明 |
|------|------|
| git commit 前 | 核心链路：提交前过一遍扫描清单 |
| PR 创建前 | 全量扫描，输出分类报告附在 PR 描述 |
| 涉及认证/支付/用户数据 | 额外深度检查 |

## 🧠 Threat Model First（v1.3 新增 — 先威胁建模再写码）

> 参考 addyosmani/agent-skills。**写码前 30 秒威胁建模**，比事后审计便宜一个量级：

```
数据流: 数据从哪来 → 经过哪 → 存哪 → 给谁看?
资产:   最值钱的是什么(用户数据/密钥/支付)?
攻击面: 输入口/接口/文件/网络边界在哪?
威胁:   最常见的 3 个(按 OWASP Top 10 对号入座)?
```

**三层边界系统（Always Do / Ask First / Never Do）**：
| 边界 | 操作 |
|------|------|
| **Always Do** | 鉴权、输入校验、输出转义、密钥环境变量、HTTPS |
| **Ask First** | 危险命令(rm -rf/sudo)、生产数据操作、降级安全措施 |
| **Never Do** | 硬编码密钥、明文密码存储、eval 用户输入、绕过鉴权 |

## 🔍 扫描维度（六项清单）

### 1. 权限验证
- [ ] 接口/路由是否有鉴权？（不能裸奔）
- [ ] 权限判断是否在服务端？（不能只靠前端隐藏）
- [ ] 是否存在越权（IDOR：改 ID 就能访问他人数据）？
- [ ] 管理员操作是否单独校验角色？

### 2. 状态与数据安全
- [ ] 敏感状态（登录态/token/会话）是否加密存储？
- [ ] 密码是否哈希存储（bcrypt/argon2），禁止明文？
- [ ] 用户输入是否做注入防护（SQLi/XSS/命令注入）？
- [ ] 响应是否泄露内部信息（堆栈/路径/SQL）？

### 3. 网络与传输
- [ ] 生产环境是否强制 HTTPS？
- [ ] 外部 API 调用是否校验响应（SSRF 防护）？
- [ ] 回调/Webhook 是否有签名验证？

### 4. 密钥与配置
- [ ] 是否有硬编码密钥/密码/token 提交进 git？（git log 历史也要查）
- [ ] 密钥是否走环境变量/密钥管理（本项目惯例：.env）？
- [ ] .gitignore 是否排除 .env/config 敏感文件？

### 5. 依赖与供应链
- [ ] 新增依赖是否来自可信源？
- [ ] 依赖版本是否锁定（lockfile）？
- [ ] 有无已知高危 CVE 的依赖？（`pip-audit` / `npm audit`）

### 6. 日志与审计
- [ ] 日志是否记录关键操作（登录/删除/支付）？
- [ ] 日志是否避免记录敏感信息（密码/token/完整身份证）？
- [ ] 失败操作是否留痕（防抵赖）？

## 📊 输出分类报告

```markdown
# 安全审计报告 — <项目/模块>
- 审计时间：<时间戳>
- 审计范围：<文件/模块列表>

## 🔴 已达标（通过）
- <项> ✅

## 🟠 需优先处理（提交前必须修）
- <问题 + 位置 + 修复建议>

## 🟡 后续优化（可排期修）
- <问题 + 建议>

结论：🟢 可提交 / 🟠 修复后提交 / 🔴 禁止提交
```

## 🔄 审计流程

```
1. 代码生成完成 → 按六项清单扫描（核心检查项逐条过）
2. 发现问题 → 修复（小问题直接改，大问题走 systematic-debugging 定位）
3. 重扫确认 → 输出分类报告
4. 通过后 → 才允许 git commit（配合 git-workflow）
5. 高风险项记录到 .snapshots/ + global-experience（沉淀为经验）
```

## 🛠️ 工具化扫描（v1.2 — 清单 + 工具双轨）

> v1.2 起,六维清单之外**强制跑工具扫描**兜底(AI 自查自己的代码不可靠)。
> 工具命令与 `code-security` skill 联动——code-security 管"扫描+修复",本 skill 管"闸门+汇总"。

```bash
# 提交前一键四扫（核心,必跑）
semgrep scan --config auto .            # SAST: SQLi/XSS/命令注入/路径穿越等(CWE 标注)
gitleaks detect --source . --redact     # git 历史密钥泄露
pip-audit / npm audit                   # 依赖 CVE(按项目语言)
git diff | semgrep scan --config auto --json -   # 增量扫描:只审本次改动

# 依赖 CVE 详情
pip-audit --requirement requirements.txt   # Python
npm audit --json                            # Node
```

扫描结果并入下方分类报告:
- 🔴 高危(密钥硬编码/SQLi 等)→ **禁止提交**,修完重扫
- 🟠 需处理 → 修复后提交
- 🟢 干净 → 通过,进入 commit

> 排障:semgrep 装不上用国内镜像(`pip install semgrep -i https://pypi.tuna.tsinghua.edu.cn/simple`);
> 误报多 → `.semgrepignore` 排除生成目录。完整命令/规则见 `code-security`。

## 🎯 误报反馈与规则分级（v1.1 新增 — 防"狼来了"效应）

**目的**：误报率过高会摧毁用户信任——前 10 次 8 次误报，第 11 次真泄露来了也被忽略。

### 规则分级（不可一律同权）

| 级别 | 示例 | 处置 |
|------|------|------|
| 🔴 致命 | 密钥硬编码、SQL 注入模式 | 永不降级，零误报容忍 |
| 🟠 高危 | 权限过宽、依赖漏洞 | 可下调敏感度，但不可关闭 |
| 🟡 中危 | 日志泄露、注释含 TODO | 用户可配置"信任此项目"后跳过 |
| 🟢 提示 | 代码风格、文档缺失 | 仅完整模式显示，/simple 隐藏 |

### 误报标记机制

- 每次审计报告，用户可标记"误报"并说明原因 → 写入 `~/.vibe/security/false-positives/`
- 同类误报 ≥3 次 → 自动下调该规则权重（🟠🟡 级；🔴 级永不降级）
- 每季度重置低权重规则，防止规则"睡死"

### 报告 UX（v1.1 — 摘要优先，重点展开）

```markdown
# 安全审计摘要 — <项目/模块>
本次扫描发现 2 项需关注（其中 1 项高置信度）。

## 🔴 高置信度（置顶，强制查看）
- <问题 + 位置 + 修复建议>

## 🟠 需处理（可折叠）
- <问题>

## 🟡/🟢 低置信度（默认折叠）
- <列表>
```

> 不是"列表轰炸"，而是"风险摘要 + 重点展开"——低置信度折叠，高置信度置顶红色。

## 快速排障

| 症状 | 处理 |
|------|------|
| 不知道查哪些文件 | 按本次改动 diff 范围审计（git diff） |
| 密钥已提交进 git | 立即轮换密钥 + 清理 git 历史 |
| 审计太慢 | 核心六项全查，深度项按风险等级抽样 |
